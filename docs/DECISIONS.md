# Decision log

Decisions taken during the build, with the reason. Where docs/ARCHITECTURE.md or
docs/INTERFACES.md and this log disagree, fix the docs: this log is the history.

|---|---|---|---|---|

| D7 | 2026-10-11 | Testnet collateral denominations: **0.01 TAZ and 0.05 TAZ** (was 0.1 / 0.5 / 1) | The only working post-NU7 faucet gives 0.125 TAZ per IP per day | deposit flow, amount fingerprinting (L3), demo |

| D10 | 2026-10-11 | GitHub repo `Himess/zecured` is **private**; it becomes public only when Semih decides (submission deadline 2026-10-28) | Owner's instruction | publishing |
| D11 | 2026-10-11 | Liquidation dust guard: seized ≥ **100,000 zat** (0.001 ZEC) **or** seized = the vault's entire remaining outstanding; no floor on the remainder (was: seized ≥ 0.01 ZEC; then briefly also "remainder 0 or ≥ 100,000 zat") | With 0.01 TAZ vaults a full-debt liquidation just past 62.5% LTV seizes ~707,000 zat, so a 0.01 ZEC floor made those vaults unliquidatable until 88.75% LTV (bad debt). 100,000 zat is still 10× the payout fee. A remainder floor left positions with 100,000–200,000 zat and remaining debt unliquidatable between 62.5% and 88.75% LTV. A sub-floor remainder stays with the borrower (dust in the vault if it is below the payout fee) | Adapter, payout queue |
| D12 | 2026-10-11 | zZEC's "expected transfer from Morpho" is bound to the caller: `expectFromMorpho(maxAmount)` arms a one-shot (msg.sender, max) pair in transient storage, set right before the Morpho call that moves zZEC | Spike C: an explicit recipient argument is unnecessary attack surface; for liquidation it must be armed before `Morpho.liquidate` because Morpho transfers collateral before the callback | ZZEC, Registry, Adapter |
| D13 | 2026-10-11 | `CloseRequest` carries the quoted `marginBps` (capped by the Adapter) besides `minUserAmount` | The margin differs per market maker quote; the borrower signs exactly what was quoted, `minUserAmount` still guards against price moves | Adapter, app, market maker bot |
| D14 | 2026-10-11 | Partial collateral withdrawal: `requestPartialRelease(vaultId, amount, destCommitment)` by the account; `MIN_RELEASE` (100,000 zat) ≤ amount ≤ outstanding − `MIN_RELEASE` (the rest stays payable on its own); besides Morpho's LLTV check the Registry requires the post-withdrawal LTV to stay ≤ 50%; emits the same `ReleaseRequested` (Release claim); the vault stays active | Roadmap item: borrowers can take part of their ZEC back without closing; the signer ledger already pays any Release claim amount with change back to the vault (I10). The stricter LTV keeps users away from immediate liquidation | Registry, signer claims, app, paymaster allowlist |
| D15 | 2026-10-11 | Optional random attestation delay (leak vector L5): the coordinator waits `N + d` confirmations, `d` uniform in `[0, attest_delay_max_blocks]`, drawn once per vault (0 in the demo) | Breaks the exact deposit → mint timing on mainnet-like volume; signers only enforce the N-confirmation minimum | coordinator config |
| D16 | 2026-10-11 | Coordinator → node requests are authenticated: the coordinator signs `(method, path, sha256(body), timestamp)`; nodes accept only the configured coordinator address within ±60 s | Prerequisite for independently operated nodes on the open internet (DoS and probing); authorization of payouts still rests on each node's own policy checks | node API, coordinator |

| D17 | 2026-10-11 | Each node reads Zcash and Base through its own sources, optionally checked against witnesses that must agree (deposit block hash, transaction bytes and tip; Registry state by `eth_call`); Registry logs are accepted only from the Registry and only if not removed | Security review C-1 / C-2: a node is as honest as its chain data; one shared source made it a single point of failure | node, base-client, [OPERATORS.md](OPERATORS.md) |
| D18 | 2026-10-11 | The demo "compromised" mode is compiled only with the node's `demo` feature and allowed only on nodes started with `--demo-allow-compromise` (nodes 4 and 5 in the demo); mode switches need the coordinator's signature | Security review C-3: the switch must never be able to lift policy on three nodes | node, backend, scripts |
| D19 | 2026-10-11 | A vault's books contain only its deposit and the planned change of its own transactions; nodes record the txid of the payout they signed, never sign a different one while it can still be mined, and confirm only that txid | Security review H-1 / H-2: payouts could be misattributed, and foreign or zero-value notes could freeze a vault or inflate fees | node, policy, coordinator |
| D20 | 2026-10-11 | All five signers sign `VaultOpened` (vault, owner, account, amount, expiry, hashes of the address and the UFVK) at the end of the DKG; the app and the CLI verify the signatures against a signer set pinned in the build before showing the deposit address; contract addresses are pinned in the app build as well | Security review C-4 / H-6: the deposit address and the contract addresses must not depend on trusting the backend | node, coordinator, backend, app, CLI |
