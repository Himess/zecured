| D11 | 2026-10-11 | Liquidation dust guard: seized ≥ **100,000 zat** (0.001 ZEC) **or** seized = the vault's entire remaining outstanding **or** the liquidation clears all the borrower's debt (added after the contracts review, L-1: with D14's 100,000 zat floor a small position could otherwise not be liquidated between LLTV and ~89 % LTV); no floor on the remainder (was: seized ≥ 0.01 ZEC; then briefly also "remainder 0 or ≥ 100,000 zat") | With 0.01 TAZ vaults a full-debt liquidation just past 62.5% LTV seizes ~707,000 zat, so a 0.01 ZEC floor made those vaults unliquidatable until 88.75% LTV (bad debt). 100,000 zat is still 10× the payout fee. | D19 | 2026-10-11 | A vault's books contain only its deposit and the planned change of its own transactions; nodes record the txid of the payout they signed, never sign a different one while it can still be mined, and confirm only that txid | Security review H-1 / H-2: payouts could be misattributed, and foreign or zero-value notes could freeze a vault or inflate fees | node, policy, coordinator |
| D20 | 2026-10-11 | All five signers sign `VaultOpened` (vault, owner, account, amount, expiry, hashes of the address and the UFVK) at the end of the DKG; the app and the CLI verify the signatures against a signer set pinned in the build before showing the deposit address; contract addresses are pinned in the app build as well | Security review C-4 / H-6: the deposit address and the contract addresses must not depend on trusting the backend | node, coordinator, backend, app, CLI |
| D21 | 2026-10-11 | `closeWithCollateral` takes a `maxRepayAssets` chosen by the executor, and the market maker repays at most its quoted debt plus 10 bps of interest; it remembers its quotes and refuses a close without a live quote | Contracts review L-2: a borrower could borrow more after signing a close request and make the market maker repay several times the quoted debt | SettlementAdapter, bots |
| D22 | 2026-10-11 | Tier 2 deposit proofs (docs/TIER2.md): a RISC Zero zkVM proof that a v6 Ironwood-only transaction (D5) is in a block committed by a later header (txid path → header `merkleRoot` → ZIP 221 history-tree leaf, path and peaks → that header's `hashBlockCommitments`), creating a note of the vault's amount to the vault's address that the vault can decrypt, in a block at or below the vault's expiry height. The journal is (anchor header hash, vaultId, account, amount, tag, `VaultOpened` struct hash); `Registry.attestDepositWithProof` requires the anchor on the header relay's best chain with `minConfirmationWork` on top, **all five** signers' `VaultOpened` signatures over that struct hash, and the proof. Proven against the inclusion path of the transaction rather than the note commitment tree (no Sinsemilla Merkle path); the deposit's block stays private, only the anchor header is public | Removes the signers as deposit attesters and the light wallet server as a data source for minting. RISC Zero after comparing zkVMs on this machine (8 GB, no Pallas precompiles anywhere; RISC Zero's 256-bit modular multiplication accelerator cuts Pallas field arithmetic ~3×) and on Base Sepolia (verifier router deployed). The address and viewing-key hashes stay inside the proof: a sender who knows the vault's address (an exchange paying into it) cannot find the vault on Base. All five signatures because the DKG needs all five anyway, so one honest signer can refuse a vault key it did not create | tier2/, Registry, deploy script |
| D23 | 2026-10-11 | `Registry.cancelVault(vaultId, sigs)`: 3 of 5 signers can mark a never-activated vault `Cancelled`; neither an attestation nor a proof can activate it afterwards. A conforming deposit may be refunded only once its vault is cancelled on Base | Security review L-8 (a conforming deposit that can never be attested had no refund path), and required by D22: anyone holding a deposit proof can mint without the signers, so refunding an unminted conforming note is safe only after the vault can no longer be activated | Registry, signer refund policy |
| D24 | 2026-10-11 | The deposit tag is BLAKE2b-256 keyed with BLAKE2b-256("Zecured_TagKey__", vault UFVK string) over the note commitment `cmx`, for attestations (signers) and proofs alike (was: keyed by the vault `sk` over the nullifier) | A deposit proof cannot use the signers' secret `sk`; one definition gives the same tag for the same note on both paths, so a note can never mint twice. Still unlinkable without the viewing key (L9) | policy, node, tier2/statement |
| D25 | 2026-10-12 | `MintMode` is immutable. The Base Sepolia deployment is `ProofOnly`: `attestDeposit` reverts and vaults are activated only on deposit proofs. `SignerAttested` (both paths) stays for the local fork, and the deploy script refuses it elsewhere without `ALLOW_SIGNER_MINT=true` | Review K1: with both paths open, minting is only as safe as the weaker one; three signers, or one lying light wallet server, could mint unbacked zZEC through an attestation. It is also the premise of Tier 3: theft can only be proven against collateral that provably exists | Registry, deploy script, coordinator |
| D26 | 2026-10-12 | A deposit proof only reserves the vault, its tag and its account (`ActivationPending`). `finalizeActivation` mints once the relay's best chain has gained `finalizeDepth` (6) headers and `finalizeDelay` (150 s) has passed, with the proof's anchor still on the best chain under `minConfirmationWork` (3.5 M, about ten normal NU7 Testnet blocks); `dropPendingActivation` frees everything once the anchor left the best chain, and the note can be proven again. Cancellation waits while a proof is pending. The seal must start with the pinned verifier selector | Review K3 and Y1: a lagging feeder lets an attacker feed a branch of their own and prove a deposit in it; the depth and the delay give the honest feeders time to replace that branch before anything is minted. Height alone could be fed by the attacker, time alone could pass with no feeder running. Pinning the selector fixes the verifier the router uses, while keeping the router's emergency stop | Registry, coordinator, CLI |
| D27 | 2026-10-12 | `VaultActivated` carries the deposit tag, and the signers root a vault's lineage at the note Base activated it with, whatever P1 decided. If they cannot see that note, every refund of the vault halts. A refund of a note of the vault's amount waits for 2N confirmations. P1 and the deposit statement apply the same two functions: the strict D5 check (v6 of the NU7 epoch, only an Ironwood bundle, outputs enabled) and the vault's published receiver (a note to another diversified address of the vault is `WrongReceiver`) | Review K2: P1 rests on the light wallet server's answers while a deposit proof needs no signer, so a node's own classification could differ from what was minted; a refund of the note that backs zZEC would leave it unbacked. With the same predicates, a deposit P1 accepts is one a proof can prove, and the reverse | node, coordinator, policy, tier2/statement |
| D28 | 2026-10-12 | The deposit guest is built once, exported (`zecured-tier2-host export-elf`), and every prover runs that file (`ZECURED_DEPOSIT_ELF`); its image id is what the Registry pins | The image id depends on the build machine: panic messages carry the source paths of the guest's dependencies. A prover that rebuilt the guest elsewhere would compute another image id and its proofs would be refused | tier2/host, coordinator, deploy |
